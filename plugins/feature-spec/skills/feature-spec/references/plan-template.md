# Plan template

Two skeletons: `plan.md`, which is the map, and `tasks/T0N.md`, which is the
work. **What goes in each section is fixed; what it says is not.** A section with
nothing to say says so — it is never padded and never deleted, because a reader
cannot tell a deleted section from one nobody thought about.

The plan is read by a person picking up the work and by an agent executing it.
That is what the identifiers, the `Covers:` tags and the quoted done-conditions
are for.

## Contents
- `plan.md`
- `tasks/T0N.md`
- Slot rules
- The task file is the source; the task graph is generated
- Covers tags — every task
- A done-condition is quoted, never restated
- Enabling work, plan assumptions and open questions
- What the plan never contains

## `plan.md`

```plan-skeleton
# Implementation plan: Retry uploads

Spec: docs/specs/2026-08-21-retry-uploads/spec.md
Record: docs/specs/2026-08-21-retry-uploads/tree.md
Tasks: 4   Milestones: 2

## Approach

Sweep the checkpoint on a timer with one in-flight batch, as the spec's chosen
approach settles. The plan adds the order: attempt state has to survive a restart
before anything can act on it, so persistence lands first and every other task
depends on it.

## Seams

Where the change lands. Every path comes from the record and resolves.
- cmd/ingest/state.go:31 — the checkpoint struct   ← Grounding fact 1
- cmd/ingest/replay.go — the nearest analogous feature   ← Grounding fact 2

## Milestones

- **M1 — P1 shippable slice**: T01, T02 — the importer resumes from a checkpoint.
- **M2 — P2**: T03, T04 — the attempt ceiling and the reject file.

## Task graph

| Task | Title | Covers | Depends on | Milestone | Status |
|---|---|---|---|---|---|
| T01 | Persist attempt counts in the checkpoint | FR-003 | — | M1 | Planned |
| T02 | Resume from the checkpoint on start | FR-001, SC-001 | T01 | M1 | Planned |
| T03 | Enforce the attempt ceiling | FR-002 | T01 | M2 | Planned |
| T04 | Write rejected rows to the reject file | SC-002 | T03 | M2 | Planned |

## Not planned

Requirements and criteria this plan deliberately leaves out, with the reason.
- _nothing — every requirement and criterion is covered by a task_

## Enabling work

Tasks no requirement asked for directly, with what each one unblocks.
- _none — every task covers at least one requirement_

## Plan assumptions

Implementation decisions the spec did not settle. Each names its reversal cost.
- The attempt counter is a field on the existing checkpoint struct rather than a
  sidecar file. — **Reversing:** a migration of every checkpoint written since M1.

## Open questions carried from the spec

- [NEEDS CLARIFICATION: per-source overrides — low impact, deferred to post-launch]

## Lessons

Filled after the work ships. Empty until then.
```

## `tasks/T0N.md`

```task-skeleton
# T01 — Persist attempt counts in the checkpoint

Covers: FR-003
Depends on: —
Milestone: M1
Status: Planned
Touches: cmd/ingest/state.go:31

## Goal

The checkpoint carries a per-row attempt count that survives a process restart.

## Why now

Nothing else can be built on attempt state until it survives a restart, so this
is the task T02 and T03 both wait on.

## Action items

- [ ] Add an attempts field to the checkpoint struct at cmd/ingest/state.go:31
- [ ] Write it whenever a retry is scheduled
- [ ] Round-trip it through the existing checkpoint encoder

## Done when

Quoted from the spec, not restated.
- FR-003  Given a retry is scheduled, when state is written, then it lands in the checkpoint file.

## Notes

The encoder is shared with `--replay`, so a field added here appears there too.

## Execution summary

Filled when the task completes. Empty until then.
```

## Slot rules

| Section | Rule |
|---|---|
| `## Approach` | The spec's chosen approach in its own terms, then **what the plan adds** — the order, and why that order. If it only restates the spec, the plan had no sequencing thought in it. |
| `## Seams` | Real paths, from the record's grounding facts, each with its source tag. `check-plan.sh` resolves every one; a file the work creates is written `path (new)` and is not resolved. A seam nobody could find is a plan built on a guess. |
| `## Milestones` | **M1 is the P1 slice and nothing else.** The spec already guarantees P1 alone is shippable; a first milestone that reaches into P2 has thrown that guarantee away. |
| `## Task graph` | **Generated by `make-progress.sh`.** Never hand-edited — the task files are the source, and a hand-edited table is a second copy that drifts. |
| `## Not planned` | Every FR and SC no task covers, with the reason (R18). Empty is written as `_nothing — …_`, never deleted. |
| `## Enabling work` | Tasks covering no requirement, with what each unblocks (R19). Legal, and never silent. |
| `## Plan assumptions` | One line per decision the spec did not settle, in the form `- <decision> — **Reversing:** <cost>` (R21). The dash form is checked. |
| `## Open questions` | Every `[NEEDS CLARIFICATION]` the spec carries, copied intact (R20). |
| `## Lessons` | Written after the work ships, by whoever shipped it. Not this command's output. |

| Task field | Rule |
|---|---|
| `Covers:` | The FR and SC identifiers this task delivers, comma separated. `—` only for enabling work, which `plan.md` must then list. |
| `Depends on:` | Task ids, comma separated, or `—`. Checked for existence and for cycles. |
| `Milestone:` | One milestone id, declared in `plan.md`. |
| `Status:` | `Planned` · `In progress` · `Done` · `Blocked`. Nothing else parses. |
| `Blocked by:` | Present only on a `Blocked` task. Names a task id or an open marker, verbatim. |
| `Touches:` | Real paths, comma separated. Resolved by the checker. A file this task **creates** is written `path (new)` and is not resolved. Omit rather than guess. |
| `## Action items` | Checkboxes, one verifiable edit each. No unquantified adjectives — the same rule the spec's criteria are held to. |
| `## Done when` | **Quoted** acceptance scenarios and success criteria, verbatim from the spec. |
| `## Execution summary` | Empty until the task completes. This command never fills it. |

## A path the work creates is written `(new)`

A plan that adds a file names a path that does not exist yet, and that is not a
hallucination — it is the point of the task. Write it as
`Touches: cmd/ingest/retry.go (new)` and the checker skips the existence test for
that entry alone.

This is deliberately explicit rather than inferred. Downgrading the check to a
warning for every unresolved path would let an invented seam through in exactly
the case the check exists for; making the honest case *sayable* keeps the rest
strict.

## The task file is the source; the task graph is generated

Every status lives in exactly one place: the task file's `Status:` line.
`plan.md`'s task-graph table is regenerated from the task files by
`make-progress.sh`, and `check-plan.sh` fails if the two disagree.

This is deliberate, and it is the one place this plan format departs from the
structured-plan-mode design it otherwise follows. That design asks for a status
kept in three places at once — the task file, the plan, and a native task list —
which is three chances to update two of them. A number recomputed from its source
cannot fall behind it, and the plugin already takes exactly this line with the
design record's protocol counters.

## Covers tags — every task

`Covers:` is to the plan what a source tag is to the spec, and it is checked the
same way: every identifier is resolved against `spec.md`, not merely shape-matched.
A task claiming `FR-042` where the spec defines no `FR-042` fails as a fabricated
citation.

| ✗ Not a Covers value | ✓ A Covers value |
|---|---|
| `Covers: the retry work` | `Covers: FR-002, FR-003` |
| `Covers: FR-042` when the spec stops at `FR-009` | `Covers: —` with an `## Enabling work` entry |

The check runs in both directions. Forwards: every identifier a task claims
exists. Backwards: every identifier the spec defines is claimed by some task, or
listed under `## Not planned` (R18). **Backwards is the one that matters** — a
plan that silently drops a requirement reads exactly like a plan that covers it.

## A done-condition is quoted, never restated

The spec already wrote the acceptance scenario. Restating it in the task file
produces two versions of one condition that drift, and the drift always favours
the easier one.

| ✗ Restated | ✓ Quoted |
|---|---|
| `- Attempt counts persist correctly` | `- FR-003  Given a retry is scheduled, when state is written, then it lands in the checkpoint file.` |

`check-plan.sh` looks each quoted line up in the spec. A done-condition the spec
does not contain fails as a fabricated quote — the same failure class as a
fabricated citation, for the same reason.

## Enabling work, plan assumptions and open questions

These three sections are where an honest plan differs from a tidy one.

**Enabling work is real.** Extracting a seam, adding a migration, writing a test
harness — no requirement asks for any of it, and a plan that pretends otherwise
either hides the work or invents a requirement to justify it. The rule is not
*don't*; it is *say so, and say what it unblocks* (R19).

**Plan assumptions are unavoidable.** The spec states behaviour and refuses to
name a type, a library or a function — so **every** technology choice in the plan
is a decision nobody has made yet. Recording them with a reversal cost is what
stops the plan reading as though the interview settled them (R21). A plan with an
empty assumptions section on a non-trivial feature is not a plan without
assumptions; it is a plan whose assumptions are invisible.

**An open question is not a task.** A marker the spec carries stays a marker.
Planning around it — picking the answer quietly, in an action item — is the
failure R20 exists for. Either the task is `Blocked by:` that marker, or the
requirement goes under `## Not planned` naming it.

## What the plan never contains

No requirements — those are the spec's, and a plan that restates them has forked
them. No estimates in hours or days: the interview never asked, so a number here
is invented, and R11 is the same rule it always was. No code. No implementation —
this command writes the plan and stops.
